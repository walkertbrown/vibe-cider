# Actual — 2026-09-13

## The flow at phone size

A Product Hunt launch is mostly phones, and until tonight nothing had ever
made a book at phone size — `test:perf` measured first load on a throttled
phone, and that was all. So: `npm run test:mobile`, which runs the whole
flow on a real device profile and fails on anything a thumb would hit.

It lands, checks nothing scrolls sideways (naming the widest offending
element when it does, so a failure is actionable), checks every control in
the tool is at least 36px tall, switches to crosswords — the type with the
most on screen — makes a real 14-puzzle book and its cover, opens the
unlock dialog and checks it fits and its email box is tappable, then visits
the five pages a launch links to at the same width. Runs on **iPhone SE
(320px), iPhone 13 (390px) and Pixel 7 (412px)**; all three green, and the
books are Ghostscript-clean 24-page PDFs made entirely on the phone.

**One real bug found.** At 320px the two-up rows truncated their select
labels — Trim size read *"6" × 9" — most c…"*, which is exactly the sort of
thing that looks fine from a desktop and makes a phone user think the tool
is broken. The rows now stack below 481px and stay side by side above it.
A `noTruncation` check is part of the suite so it cannot come back.

Also fixed while there: the suite took the device name only as the second
argument, so passing a name without a URL tried to navigate to "iPhone SE/".
It now reads either argument in any order.

Perf unchanged (251 KB, 0.96 s to first puzzle); browser suite green.

## Making stale copy a test failure

Four times this week a claim on a page was true when written and false when
read — the launch file, the pricing block, the demo caption, the home page's
own `<title>`. Re-reading everything after every change does not scale.
`test/copy.test.js` now runs with the unit suite, offline, over every
published page and every marketing file, and asserts two things:

**1. A number in the copy must equal the number in the code.** Themes,
the size of the clue table, the price, KDP's page minimum and maximum, the
sudoku expert clue count, and the maze size range — each read from the
module that defines it. Patterns are deliberately narrow: a sudoku's "26
clues" must not be mistaken for the size of the clue table, so that rule
only matches four-digit counts; the maze range is checked as a pair
("15×15 up to 39×39") rather than every square grid on the page.

**2. A page that discusses the puzzle types must know all of them**, and no
page may miscount them. The count rule only matches product claims — a note
saying an old video "shows three types" is describing the video, and is
true — which took two passes to get right.

**It found real drift immediately:** "1,400 clues" on the landing page,
in the Product Hunt file and twice in the HN post. The table has 1,460.
Written before the last 60 clues existed and never updated — exactly the
kind of small wrongness that a stranger checking the claim would find, and
exactly what I have been catching by luck until now.

Then I checked the test can fail: injected "1,410 clues" and "All four also
offer" into the landing page, confirmed both were caught, restored the file.
A test I have not seen fail is a test I do not believe.

80/80 unit. Deployed; SEO suite still clean.

## Does the ink stay inside the margins? Now checked in pixels

Every other check on the interior is arithmetic — the code works out a
gutter, and a test asks the code whether it worked out the gutter. None of
it would notice a page that draws *outside* the box it was handed, which is
the single thing KDP rejects files for.

`npm run test:ink` rasterises the real PDF at 100 dpi in greyscale and looks
at every pixel: for six book types (including 6×6 sudoku) × three trims ×
free and paid, every pixel darker than mid-grey must fall inside that page's
safe area, with the gutter on the correct side for odd and even pages. One
pixel of tolerance for the rasteriser rounding a glyph edge; a failure names
the book, the trim, the page, which margin, and the coordinate.

**Two real faults on the first run, in code that has been live all week:**

1. **The maze's "start" and "end" labels sat in the margins.** They are
   drawn outside the grid by design, but nothing reserved room for them, so
   on every trim "start" landed about 0.1" inside the gutter — the binding
   edge, the worst place for it. The maze is now sized to leave room for both
   labels, and `drawMaze` clamps them to the page box it is given. (The
   six-up solutions sheet passes no box and draws no labels — there was
   never room for them there, and they were never drawn.)

2. **The sudoku grid's outer border straddled the safe-area edge.** A stroke
   sits centred on its path, so half of the 2.2pt outer line — 1.1pt — was
   past the boundary on a full-page grid. Now the outer lines are inset by
   half their width, so the ink ends exactly where the box does.

Neither would necessarily have been rejected — 0.1" into a 0.375" gutter is
tight, not fatal — but both are precisely what KDP's previewer flags, and
"your file was flagged" is the one thing this product must never cause.
Found by looking at pixels, which is the only way they could have been.

Samples and pins regenerated with the fixed renderer, so what is published
matches what the tool now makes. 80/80 unit, pdfcheck, browser, graded and
links green.

## "Ask for fifty, get fifty" — checked for every type (boss's question)

The boss asked whether I had checked how many puzzles each type actually
puts in a book. I had not, other than for word search. The original disaster
of this project was the screen saying 50 and the file holding 5, so this was
the right question.

**Every built-in theme is fine**: all five types deliver exactly the count
asked for, at 1, 14 and 50, numbered 1..n with no gaps, from the thinnest
themes (American States: 37 long words) as well as the fattest.

**A thin pasted word list was not fine.** Eight three-letter words that
barely share letters produce **zero** criss-cross or crossword puzzles —
and the tool was happy to build the "book": three pages of front matter and
five ruled pages, an 8-page file, while the line above the button still
said "50 puzzles · 66 pages". That is the Notes-page failure exactly, in a
new type, and I shipped it on Friday.

Three fixes:

1. **The generators say it once.** They were pushing one warning per failed
   puzzle — fifty identical lines, which is not a warning but a wall. Now a
   single line that distinguishes the two cases: "*None* of these words can
   make a criss-cross: they need to be at least three letters and to share
   letters with each other so the grid can interlock" versus "*12 of 50*
   could not be built and were left out".
2. **The tool refuses to build an empty book** — "Nothing to put in the book
   — see the note above" — instead of handing over ruled paper. If it is
   merely short, the status says so while it works: "Laying out 38 puzzles
   (12 could not be built)…".
3. **The preview no longer lies.** With nothing to show it was leaving the
   *previous* type's puzzle on screen, which reads as success. It now says
   no puzzle could be made and where to look.

`test/counts.test.js` covers all of it: every type × four themes × three
counts delivers exactly what was asked and numbers it correctly; a too-thin
list warns once, never silently; indexes have no gaps when puzzles are
dropped. Verified in a live browser too — preview message, warning and
refusal all correct, no console errors.

83/83 unit; criss-cross, crossword, browser and wordlist suites green.

## The preview was showing puzzles the book does not contain

Same thread as the boss's question — what is on screen versus what is in the
file. The last unchecked member of that family was the preview itself.

**It was lying on every graded book.** The preview builds three puzzles and
the grading spreads the four bands across *the number of puzzles in that
book* — so the preview graded three puzzles as easy, medium, hard, while the
first three pages of the fifty-puzzle file are all easy. For sudoku and
mazes the difficulty *is* the puzzle, so preview 2 and 3 were not merely
mislabelled, they were different puzzles from the ones that download.

Fixed: every generator takes `gradeCount` — how many puzzles the grading
spreads over — so the preview grades as the first three of the real book.
Verified puzzle by puzzle: for all five types, preview 1–3 are now byte-
identical to book 1–3, title and grid.

Two consequences, both handled honestly rather than by reverting:

- The preview of a graded book now shows three easy puzzles, because that is
  what the first three pages are. The nav line says so: **"Puzzle 3 of 50 —
  showing the first 3"** instead of "3 / 3".
- Read alone, three easy puzzles undersell a graded book. So the line above
  the preview now ends **"· graded, easy at the front to expert at the
  back"** (hard, for word search — its top band). True, and it explains what
  the reader is looking at.

`test/counts.test.js` gains a fifth case: for each type, preview 1–3 must
match book 1–3 by title and by a fingerprint of the actual grid. 84/84 unit;
browser, graded, defaults, shortbook, kids sudoku, criss-cross and crossword
suites all green against production.

## The reproducibility promise: true, but it had a hole

The FAQ says: *"Each book has a seed — put the same seed and settings back
in and you get the identical book."* Never tested. It is true: for all five
types (and 6×6 sudoku), the same seed and settings produce byte-identical
puzzles, and a different seed produces a different book. The rendered PDFs
differ only in their `ModDate` timestamp — the pages themselves are the same
ink. Now a unit test, so it stays true.

**The hole: if you lose the file, you have lost the seed too.** The promise
assumed you wrote it down. So every book now records how it was made —
type, count, difficulty, grid size, words per puzzle, themes, seed — in the
**PDF's own properties** (Document Properties → Subject). Invisible in
print, there for anyone who still has the file.

**And a mistake I nearly shipped in the same change.** My first version also
printed that line on the copyright page of *every* book — which would have
put "Made with Puzzle Press" inside a book somebody paid $19 specifically to
have unmarked. The pricing page promises the payment removes the footer line
and the PREVIEW mark "and changes nothing else"; a line on the copyright page
is a mark. So: printed on free books only, where a watermark already says as
much and the book cannot be published anyway; paid books keep clean pages
and carry the recipe only in the file's properties. A test asserts both.

A smaller thing caught on the way: a maze book's recipe listed "Animals",
because the word-list checkboxes are still set even for a type that ignores
them. Themes are now listed only for the types that draw on words.

FAQ rewritten to say all of this plainly, including where to look. 87/87
unit; browser, free cover, paid return, privacy, short book, ink and
pdfcheck green; samples regenerated.

## Monday's pre-launch sweep, run on Saturday — and what only the real domain shows

The launch checklist puts the full live sweep on Monday. Nothing in it needs

### The SEO suite failed with "robots.txt does not disallow the whole site"

Which is the sort of sentence that ruins a launch morning. It was a false
alarm, and a test bug of my own making.

Cloudflare injects a **managed robots.txt block** ahead of our file on the
custom domain — a Content Signals preamble and nine `Disallow: /` groups for
named AI crawlers. My check grepped the whole file for `Disallow: /` and
concluded the site was closed. It wasn't: `User-agent: * Allow: /` sits right
there, and Googlebot was never touched.

The reason I had not seen it in four days of running that suite is the thing
worth writing down: **I had been running it against `workers.dev`**, where
nothing is injected. Two hosts, one of them the one customers use, and I was
only ever looking at the other. Every live suite now defaults to
`puzzlepress.bananafest-destiny.com`; four of them had no default at all or
pointed at a local dev server, so `npm run test:browser` was not testing
production either. Fixed.

The check now parses robots.txt into groups the way a crawler does and asks
the only question worth asking: can the agents that send buyers reach the
pages.

Which raised a real decision, and I looked into it rather than reflexively
turning the block off. The nine blocked names are **training** crawlers. The
**retrieval** agents — the ones an assistant uses when someone asks it a
question *right now*, `OAI-SearchBot`, `ChatGPT-User`, `PerplexityBot`,
`Claude-User`, `Claude-SearchBot` — are not blocked, and that is the channel
that could actually send a buyer this month. `GPTBot` and `ClaudeBot`, the two
blocked names that look alarming, are those same companies' training crawlers.
`Google-Extended` governs Gemini grounding; AI Overviews inside Search are
crawled by ordinary Googlebot, which is fully allowed.

So: left on. It costs a training corpus that pays back in years, if ever, and
costs nothing on any channel that matters now. But it is a managed list on
someone else's schedule, so the suite asserts each retrieval agent can still
reach us and prints the blocked list every run. If Cloudflare adds
`PerplexityBot` next quarter, I find out from a failing test and not from a
flat month. Written up in `marketing/ai-crawlers.md`.

## The funnel was counting page loads as books, and the visitors are crawlers

I went looking at page weight before Tuesday and found the dashboard's most
important line was measuring the wrong file.

`Clicked Download (engine)` counted any fetch of `/js/chunk-*`. I had assumed
those chunks were the lazily-loaded PDF engine. So I stopped assuming and
recorded what a browser really asks for:

    on page load ......... main.js and four chunk-*.js
    on Download .......... render-*.js, cover-*.js, one more chunk, both fonts

Four chunks land on every page load. The line meaning "somebody made a book"
fired for anyone who merely opened the page. The tell was sitting in
yesterday's output: `engine 1` next to `Font fetches 0`, and a real download
needs both.

**Now it measures the file that only that action fetches.** `render-*.js` for
a book, `cover-*.js` for a cover, `main.js` for "a browser actually ran the
page". Written down in `test/funnel.mjs`, which drives three sessions that
each do exactly one thing and fails if the signals stop being distinct —
because nothing in the app declares this mapping and a bundler may move code
between chunks on any build. It caught a second one on its first run: both PDF
modules were loaded by a single `loadPdf()`, so **every book download also
looked like a cover download**. Split into `loadRender()` and `loadCover()`;
they share the heavy chunk, so the second costs almost nothing.

**Then the dashboard had my own fingerprints on it.** Having just pointed
every live suite at the customer-facing domain, a full sweep now makes dozens
of books and covers *in the funnel*. Same contamination as the Stripe sessions
this morning, one layer down. It asks Cloudflare which IP it sees us as, then
queries twice — everything, and everything from this machine — and subtracts.
Two queries rather than grouping by IP, because grouping truncates at scale
and this has to survive a day with thousands of addresses.

Also pruned `public/js/`: esbuild's splitting leaves old hashed files behind
and we were deploying two 1.3 MB copies of the engine plus seven orphans.
4.5 MB down to 1.5 MB. Safe because everything is served `must-revalidate`.

And here is what the honest dashboard says:

    Requests for the page       13
    ...that ran the app         1   <-- a real browser; the rest are crawlers
    Opened a sample PDF         4
    Made a book                 0
    Made a cover                0
    (my own machine ignored:    1240 requests)

**One human looked at this product yesterday.** Not thirteen. Twelve of those
thirteen never ran JavaScript — they were crawlers, and I had been reading
them as visitors all week. Nobody made a book. Nobody has ever opened
checkout.

I would rather know that three days before launch than three days after. Every
number I have been reporting was flattered by something: test sessions in the
payments, crawlers in the visits, page loads in the downloads. They are all
corrected now, and the product they describe is genuinely good — 89 unit tests
and 23 live suites say so. What it does not have is anyone looking at it.
That is Tuesday's whole job.

## Phase 13 — The card, which is the real first screen

Phase 12 fixed the first five seconds on the site. Almost nobody arrives at the
site cold on Tuesday, though — they arrive at a row in a feed. I had never once
looked at what that row will contain.

**Product Hunt's actual requirements**, read off help.producthunt.com rather
than remembered: thumbnail **square**, 240×240 recommended, under 3 MB, GIF
allowed; gallery **1270×760** recommended, at least two images; tagline 60
characters, description 260. Then I measured everything the launch doc names.

Both worries in the plan were real, and there was a third I had not thought of:

- **There was no thumbnail.** The doc listed eight gallery items and never
  mentioned the square image Product Hunt puts in every feed row. At 2am on
  launch night that would have been picked from whatever was lying around.
- **Every gallery image was the wrong shape.** `social-card.png` is 1200×630
  because that is the Open Graph size; `hero-book.jpg` I had shrunk to 1200×840
  an hour earlier for page weight, without thinking about its other job. And
  `gallery/04-the-tool.png` was **1920×2699** — a full-page portrait screenshot
  that a 1.671:1 frame would have shown as a sliver down the middle.
- **The tool screenshot was showing a bug I had not noticed.** It started
  mid-form, and the trim `<select>` read `6" × 9" — most comr`.

**The truncation was not a screenshot problem.** A closed `<select>` cannot
wrap, ellipsise or scroll — it clips. There was already a fix for this in the
stylesheet, written against a phone media query, with a comment quoting the
same cut-off string. It was the wrong ruler: the settings column is capped at a
fixed width, so the field is the same ~184px at 1280px as at 860px, and the
window getting wider never helped. **Every desktop visitor for weeks has been
asked to choose a trim size labelled `6" × 9" — most comr`**, and a second
control, the word-search difficulty, was cut off the same way.

Fixed by measuring rather than guessing: the column cap went 420 → 480px and
`.row` became `repeat(auto-fit, minmax(210px, 1fr))`, so a row goes two-up only
when two fields actually fit — it measures the space the row has, not the space
the window has, and cannot drift out of step again. `test/browser.mjs` now
measures every visible option's text against the box it has to fit in, at
1280/1000/860/400px, for all five puzzle types. While I was there, "List price
(USD, for the royalty estimate)" was wrapping to two lines and knocking its
field out of line with Ink; the royalty note under the button already says "at
$9.99 you keep $X a copy", so the label is just "List price (USD)" now.

**The assets themselves.** `scripts/gallery.mjs` now renders every frame at
1270×760 at 2× (2540×1520, ratio 1.671, all under 3 MB), with two new opening
frames — a Product-Hunt-shaped redraw of the card, and a puzzle page beside its

## Phase 14 — The paying moment

I walked the whole path a buyer takes, as a stranger would, on a phone and on
a desktop, against the live site: make a free book, look at what the watermark
does to it, open the ask, come back from Stripe, and get stuck. Four things
were wrong, and three of them only show up to somebody who has actually paid.

**The mark is right.** The free interior is a complete book with one grey line
centred in the footer of every page — "Made with Puzzle Press — free preview" —
and the free cover carries a large rotated PREVIEW across the front with a note
under it saying how to remove it. That is the balance the phase was there to
check: neither reads as damage, and neither could be published. Nothing to fix.

**The title page was lying about the book.** The subtitle field defaults to
"50 relaxing puzzles with solutions" and followed the puzzle *type* but not the
puzzle *count*. Puzzles is the most obvious knob on the page. Anybody who moved
it off 50 — which is most people, and is exactly what I did while walking this
— got a book whose first printed page claimed a number it did not contain. My
12-puzzle book said 50. That is the page an Amazon shopper sees in Look Inside.
The default is now a template over the count, with the singular handled, and it
still stops following the moment somebody types their own subtitle.

**A buyer who typed the wrong email hit a wall that said nothing.** The verify
endpoint's ordinary refusal was "No completed payment found for that email. Use
the exact email from your Stripe receipt." and ended there. The ordinary way to
reach it is not fraud, it is a buyer whose card sits under a different address
from the one they typed. They have paid us $19 and the product says no with no
way out. It now ends where the other refusal already did, at support.

**Worse: on the way back from Stripe, that wall was disguised.** Coming back to
`/?paid=1`, *any* "no payment found" answer was rewritten to "Stripe has not
finished recording that payment yet. Give it a few seconds and press Unlock
again — your money is fine." For the real race — back from checkout seconds
ago, session not yet recorded — that is the right answer. For the wrong-address
buyer it is true forever: they press Unlock, wait, press Unlock, and are told
the same reassuring thing every time, while the message hides the fact that the
address is wrong and never mentions support. The reassurance now gets exactly
one turn, then the real message. `test/paidreturn.mjs` pins both halves.

**And nothing told a returning buyer how to get back in.** The licence has
always been just the email — no account, nothing to expire — but on a new
laptop, or after clearing a browser, the only thing the page offered was
"Remove both — $19 one-time", which is what being asked to pay twice looks
like. There is now a second link beside it, "Already paid? Unlock", into the
same dialog, and a line in the terms that says the same thing in words.

The support address in an error is also a `mailto:` link now rather than a
string to memorise — built from text nodes, not innerHTML, because that string
comes from the server and server text is not worth parsing as markup.

Green: 90 unit tests (one new: every refusal a buyer can reach names a way
out), browser, mobile ×3, defaults (two new: the subtitle follows the count,
and a 12-puzzle book still warns it is under KDP's 24-page minimum), paid
return, links, privacy, nostorage, free cover. Deployed three times.

**One question for the boss, in FACTS terms:** is "Successful payments" turned
on in Stripe's customer-emails settings for the live account? The unlock is
keyed to the email on the receipt, and the receipt is the only place a buyer
ever sees which address that is. I cannot read that setting with the restricted
key. There are nine live checkout sessions and none of them completed, so there
is no real receipt to look at either.

## Phase 16 — The engines nobody has tested

**Actual.** Green everywhere, but not before two real things were found.

**The finding that started it.** Every test in this repository ran on Chromium
— including `test/mobile.mjs`, which launches Chromium and hands it an
"iPhone 13" profile. A device profile is a viewport and a user-agent string.
The puzzle generation, the PDF layout, the font embedding, the download: all
of it was still Chromium. The suite had said "MOBILE OK — iPhone 13" for weeks
and had never once run Safari's engine.

**Firefox** was installed and works. Full walk against production: a 50-puzzle
free book (66 pages), a licensed 60-puzzle 8.5×11 book (78 pages), the free
and paid covers, the unlock dialog, the phone-width layout, no clipped control
labels at four widths across all five puzzle types. Zero page errors.

**WebKit** was the one that mattered and the one I nearly did not get. Its
dependency check asks for two libraries via sudo. Before asking, I looked at
what was actually missing: `libwoff1` and `libavif16` are both effectively
present, and the single real gap was `libjxl.so.0.8` where the system has 0.7.
JPEG XL is a format this site never decodes, so I symlinked 0.7 into
Playwright's own lib directory and WebKit 26.0 launched. Same full walk, plus
the storage-refused walk (iOS private browsing is the common way a real
person's browser refuses localStorage) and the whole paid-return path. All
green, zero page errors, on the engine every iPhone in Tuesday's traffic will
be running.

**What was actually wrong.** Auditing the shipped bundle for APIs Safari does
not have turned up nothing dangerous — no lookbehind regex, no
`showSaveFilePicker`, no `OffscreenCanvas`; the `SharedArrayBuffer` and
`Atomics` references in the pdf-lib chunk are all `typeof`-guarded. One thing
was not guarded: `dialog.showModal()`, which arrived in Safari 15.4. On an
older iPad, clicking **Remove both — $19** would have done nothing at all — no
dialog, no error, no clue — at the exact click where the money is. Both
`showModal` and `close` now fall back to the plain `open` attribute, which
every engine has understood for years. Non-modal is worse than modal and
infinitely better than a button that silently does nothing. Deployed, and both
Chromium and Firefox re-walked after.

**Made permanent**, which was the point. `browser.mjs`, `freecover.mjs`,
`mobile.mjs`, `nostorage.mjs` and `paidreturn.mjs` all take an engine
argument. `npm run test:mobile` now runs the two iPhones on **WebKit** and the
Pixel on Chromium, because that is what those devices actually are. A new
`npm run test:engines` walks Firefox and WebKit end to end. The libjxl trick is
written down at the top of `browser.mjs` so that a future WebKit failure is a
known thing rather than a mystery.

**Done when** — met. A book and a cover have been made by two engines that are
not Chromium, against production, and the one thing that would have broken on
Safari is fixed.

The honest note: this does not prove the app survives a *real* iPhone. WebKit
on a desktop has memory a phone does not, and a 200-puzzle book is a heavy
ask. What it does prove is that nothing is engine-specifically broken, which
is the failure I could not have distinguished from "nobody was interested"
when Tuesday's dashboard read zero.

## Phase 18 — what actually happened

**The risk I planned around was not real.** `/api/verify` on an email with no
payment: 0.33s, three times, against production. Phase 14's thirty seconds was
a number about a different account on a different day. Written into the code
next to `MAX_SCAN_PAGES` with the date, so the next panic has something to read.

**The first load is fine.** Cold landing on a 390px phone at slow 4G (1.6 Mbit,
150ms RTT, 4x CPU throttle): first paint 452ms, usable preview grid **1.1s**,
124 KiB pulled. The 666 KB demo GIF is lazy and never loaded in that window.

**The first click is not.** Pressing Make my book pulls **2,155 KiB** the page
has never touched: the 1.37 MB pdf-lib/fontkit chunk and two 400 KB TrueType
files. On that same connection that is 13.5 seconds between the click and the
PDF.

**What I changed.**

- A new `src/pdf/heavy.js` — a two-line module whose only job is to hold the
  heavy chunk — dynamically imported on an idle callback after the first
  render. It is its own file because the launch dashboard reads the funnel out
  of Cloudflare's request paths, and warming through `render.js` would have
  made every visitor look like somebody who made a book. Skipped entirely when
  the browser reports Save-Data or a 2G connection.
- `download()` and `downloadCover()` now start the font and module fetches
  before generating rather than after.
- `npm run build` clears `public/js` first. It never had, so every build left
  the previous hashed bundles behind and deployed them.
- `test/funnel.mjs` gained a `warmed` signal and asserts a plain landing warms
  the chunk without looking like a book or a cover. `scripts/traffic.mjs` shows
  it as "...and did not bounce", which is a measure the dashboard did not have.

**Measured after, same throttled phone, click to PDF:**

| | click -> PDF |
|---|---|
| clicked the instant the page was usable, warm-up blocked | 13.5s |
| clicked the instant the page was usable, warm-up racing it | 12.8s |
| clicked after twenty seconds of reading the page | **8.7s** |

The honest read: somebody who clicks instantly gains almost nothing, because
the warm-up is competing for the same bandwidth. Somebody who behaves like a
real visitor — lands, reads what it is, then tries it — gains five seconds.

**The change that did nothing.** Starting the fonts in parallel with puzzle
generation, isolated locally: 20.1s before, 20.1s after. Most of the wait is
laying out pages, which cannot start until the fonts have arrived. Kept, with
the measurement in the comment instead of the claim.

**Green after all of it**, against production: browser (chromium, webkit,
firefox), freecover, nostorage, paidreturn (webkit), funnel, and mobile on
iPhone 13, iPhone SE and Pixel 7.

**Reddit.** The boss produced the account: u/wubbydubbybubby22, six years old,
23 karma, 22 contributions, no followers. Six years clears every account-age
filter, which is the one thing that cannot be fixed in a week. 23 karma clears
the low bars and fails the high ones. Recorded in `FACTS.md`; nothing built
